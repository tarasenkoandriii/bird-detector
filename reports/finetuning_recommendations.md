# Рекомендації з донавчання після перевірки джерел

Перевірено 8 листопада 2026 року. Це план експериментів, а не нові виміряні результати. Поточні ваги та залежності не змінено.

## Що підтверджують джерела

Ultralytics рекомендує заморожування для малого набору, обережне донавчання та короткий ненульовий warmup. `freeze=23` залишає голову YOLO26n для навчання; менша глибина заморожування дає більше адаптації. Загальна двоетапна схема в документації передбачає подальше розморожування моделі. Наш поділ «класифікація → bbox» — власний контрольований варіант, а не точне відтворення офіційного рецепта. [Офіційний посібник](https://docs.ultralytics.com/guides/finetuning-guide).

Рецепт випущених YOLO26 використовував 640 px, batch=128, MuSGD та значні аугментації на великих датасетах. Це джерело ідей, але не готові налаштування для наших 998 фотографій і CPU. [YOLO26 Training Recipe](https://docs.ultralytics.com/guides/yolo26-training-recipe).

Для коротких запусків `auto` обирає AdamW і сам задає LR; ручний `lr0` тоді ігнорується. Для керованого експерименту залишаємо явний AdamW. `nbs` визначає накопичення градієнтів. [Параметри навчання](https://docs.ultralytics.com/modes/train).

Аугментації мають відповідати майбутнім сценам. Mosaic може допомагати дрібним об’єктам, але ускладнює навчання; його можна вимикати наприкінці. [Посібник з аугментацій](https://docs.ultralytics.com/guides/yolo-data-augmentation).

Дослідження Kumar та співавторів показує ризик спотворення сильних попередньо навчених ознак і користь LP-FT у досліджених задачах класифікації. Це мотивація обережного розморожування, а не доказ переваги конкретного YOLO-рецепта. [Оригінальна робота, ICLR 2022](https://arxiv.org/abs/2202.10054).

## Що перевірено в установленій версії

Локальний Ultralytics 8.4.204, torch 2.2.2; перевірено `BaseTrainer.build_optimizer`, `Detect.forward`, default config і наші скрипти. Інтернет-документація оновлюється, тому назви нових аргументів не слід переносити без перевірки локального API.

- `optimizer=AdamW` заданий явно в обох етапах.
- `batch=8`, `nbs=64`: поза warmup накопичення приблизно 8 batch, тобто близько 16 кроків оптимізатора за епоху з 125 batch. Три епохи — це лише близько 47 кроків; точне число залежить від меж епох і реалізації накопичення.
- Вимкнення mosaic/scale/translate не вимикає HSV: типові `hsv_h=0.015`, `hsv_s=0.7`, `hsv_v=0.4` залишаються. У bbox-етапі `fliplr=0`; у класифікаційному він типовий 0.5.
- Bbox-етап фіксує статистику BN. BN affine-параметри bbox-гілок залишаються навчальними; «BN зафіксований» тут означає саме статистику.
- У доданих ваг `end2end=False`: активна one-to-many гілка з NMS. Не слід називати цей конкретний запуск NMS-free.
- Поточний warmup=0 — виміряний локальний вибір, але не універсальна рекомендація. При перевірці warmup потрібно явно задати `warmup_bias_lr=0.0`, щоб не успадкувати типовий 0.1 поруч із LR=1e-5.

## Рецепти для наступних контрольованих запусків

Це наші гіпотези на основі джерел та локальних результатів. Усі запуски починаються з однакового поточного `weights/best.pt`, зберігаються окремо; чинні ваги не перезаписуються.

1. **Адаптація bbox при 640 — перший пріоритет.** Ті самі 3 епохи, AdamW 1e-5, batch=8, nbs=64, заморожування та аугментації; змінити лише train imgsz 320→640. Оцінювати baseline і кандидата при однаковому val imgsz=640. Поточне збільшення лише inference-роздільності вже досліджено; це інший експеримент.
2. **Короткий warmup.** Повторити попередній контроль із `warmup_epochs=0.5`, `warmup_bias_lr=0.0`. Warmup також змінює графік накопичення градієнтів; результат оцінюємо як ефект усього warmup-режиму.
3. **М’які кольорові зміни.** Окремий запуск із `hsv_h=0.01`, `hsv_s=0.3`, `hsv_v=0.2`; геометрію не змінювати. Це кандидат для відео зі змінним освітленням, не гарантоване покращення.
4. **Навчання всієї голови.** Лише після попередніх перевірок: backbone/neck зафіксовані, обидві bbox і cls гілки навчаються разом, AdamW 3e-6…1e-5. Це потребує окремого скрипта або адаптації тренера: наявний train_boxes.py навмисно не навчає cls.
5. **Neck або весь backbone.** Нижчий пріоритет через малий набір і вартість CPU. Перевіряти лише при стійкому плато та наявності цільових відеоданих. Автоматично переходити на великий LR або MuSGD немає локальних підстав.

Готова команда для першого рецепта:

```bash
python train_boxes.py --model weights/best.pt --imgsz 640 --epochs 3 --lr0 0.00001 --name bbox640-research
python compare_models.py --skip-base --trained runs/experiments/bbox640-research/weights/best.pt --sizes 640 --report reports/bbox640_research_val.json
```

Ці команди не запускалися в межах цього огляду. Рецепти 2–4 потребують додавання відповідних керованих аргументів; наведені значення не є вже підтримуваними прапорцями train_boxes.py.

## Дані та чесна оцінка

Найважливіший для відеозадачі напрям — окрема ручна розмітка кадрів із рухом, далекими птахами, перекриттями та негативними сценами. Фонові зображення без птахів можна подавати з порожньою розміткою. [Ultralytics про фонові кадри](https://academy.ultralytics.com/courses/dataset-readiness-for-yolo/define-the-dataset-spec).

Наша пропозиція: почати з 200–400 різноманітних кадрів і 5–10% перевірених негативних сцен; ці числа — робочий бюджет, не доведений мінімум. Розділяти за вихідними відео, не за сусідніми кадрами. Позначати всіх видимих птахів, включно з дрібними, за єдиними правилами bbox.

Критерій пошуку — validation mAP50–95 при 640, з контролем mAP50/recall і FP на негативних сценах. Для переможця повторити кілька seed. Поточний test уже багаторазово оцінювався: його не використовувати для наступного вибору гіперпараметрів; для підсумкової незалежної перевірки потрібен новий закритий відео-test. Приріст не прогнозуємо до замірів.
